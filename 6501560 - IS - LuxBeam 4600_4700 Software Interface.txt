1 Introduction
This document describes the protocol that is used to communicate with the Luxbeam 4600/4700 platform over Ethernet. Functions available to LB4600, LB4700 or LB4700 C1 only are noted specifically in the document. Unless otherwise noted, all functions will be available to both platforms.






2 Overview
The Luxbeam has a Gigabit Ethernet interface that will be used to communicate with a client PC. In order for this interface to be as fast as possible, the FPGA will handle some Ethernet traffic in order to offload the CPU.

The CPU is a Microblaze processor embedded in the FPGA. The CPU will run PetaLinux operating system.


3 Units and resolutions

3.1 Autofocus linesensor resolution
The focus tracking system is based on the lateral offset of a reflected beam of light from the measurement plane. This lateral offset is detected by a 10-bit linesensor. The positional resolution and range is dependent on the laser's incident angle and the lens magnification. The resolution can also be increased through signal processing gain.

Resolution for LLS25 (1x lens):
Linesensor native resolution : 11.1 um (10-bit)
Resolution after signal processing gain : 2.775 um (12-bit) Resolution as 16-bit values : 0.1734375 um

3.2 Stepper motor resolution
A stepper motor is used to move the photohead vertically to set correct focus. Standard z-axis focus system uses a stepper motor with 400 steps/revolution connected - via a gearing of 2:1 - to screw shaft with a pitch of 1 mm/revolution.

The result is a vertical movement of 1mm (pitch)/2(gearing)/400 steps/rev= 1.25 um/step

step_size_pm = 1250000 pm/step

This can be changed to a different setting if a different z-axis is applied (see 5.9.1).

4.2 Luxbeam Proprietary Protocol
The payload data sent over UDP will be organized according to a proprietary binary protocol. This protocol is described here.

All data is transmittet using "Big-Endian" byte-ordering. Hence, a 2-byte or a 4-byte unsigned integer will


The protocol uses the payload data of UDP, and the maximum payload size is determined by the transport


UDP Maximum Payload Size
If jumbo frames of 9000 bytes are used on the Ethernet frame, the maximum UDP payload size is 8972 bytes.
This is calculated as follows:
9000 - 20 [IP header] - 8 [UDP header] = 8972.

This record is used to send a sequence text-file to the Luxbeam.


Rec nametot_sizerec_idpayload
Reply2 bytes2 bytes2 bytes2 bytes2 bytes1-8962 bytesLoadSequenceFi le11 (+)105pkg_notot_pkgdata_siz edataReplyAck
Payload:
ParameterDescriptionPermanentpkg_noSequence file package number (last package: pkg_no = tot_pkg).Notot_pkgTotal number of packages needed to send the complete file.
Max. value for tot_pkg is 20. In this case the sequence file size is 20*8962 bytes = 179240 bytes.Nodata_sizeThe number of bytes in data.NodataSequence data.No
Whenever a LoadSequenceFile record is sent with pkg_no=1, Luxbeam expects a new sequence file to be transferred. The remaining packages (if any) must be sent with increasing pkg_no until pkg_no=tot_pkg. If pkg_no is not increasing by one for each record sent, an error-reply will be sent (error = 10002).

After the last sequence data package has been sent, the ReplyAck returned will indicate if the sequence file was parsed ok (error = 0) or if there was an error while parsing (error = 10003). In the latter case, the error text explaining the parsing error can be retrieved using "Sequencer File Error Log".

If tot_pkg > 20, then an error reply = 10004 is returned.

The sequence file in text-format will be translated internally in Luxbeam. If the translated file is too large, an error reply = 10010 will be returned.

5.3.16 Sequence Label for Forward Loop
The sequence file is stored as "program" in a RAM in the FPGA. When the sequencer is started then a program counter steps through this RAM and execute task according to the sequencer commands.
Whenever a "LABEL" is seen in the sequencer then the corresponding address in the sequencer RAM is stored in a separate label ram. When "JUMP" is seen in the sequencer then the corresponding address for "jump-to label" is found in the label ram and the program counter is assigned to this value.

The label ram is generated as the sequencer program is executed and consequently the label command must be defined before jump command, i.e. no forward jump is possible.

The SetSeqLabel command can be used to manually define the label ram. If this command is used then all labels in the sequencer must be identified and manually uploaded and the automatic update that is normally done when the sequencer program finds a label command is disabled.
With this approach forward jump is possible. Example:
First column is line count, the second column is the actual address for the command in the sequencer RAM (The sequencer program is stored from address 42 and on-wards)

1 ################################################################################
2	### Assign variables and aliases 3
################################################################################
442AssignVar MemStartRow 01544AssignVar DmdStartRow 01646AssignVar InumA	01748AssignVar InumB	11850AssignVar InumC	21952AssignVar NumRows	1080110Alias	one_sec	400000011################################################################################
12	#
13	54	Label selectLoop 1
14	56	Jump selectLoop 1
15	#
16 ################################################################################
17### Seq 01858Label seq0 1


19	60	LoadRow	DmdStartRow NumRows InumA MemStartRow 173 # (1080*40ns)*(4tics/us)=172.8
2062ResetGlobal1002164Jump selectLoop 122#23################################################################################
24 ### Seq 1
25 66	Label seq1 1
26 68	LoadRow	DmdStartRow NumRows InumB MemStartRow 173 # (1080*40ns)*(4tics/us)=172.8
2770ResetGlobal1002872Jump selectLoop 129#30################################################################################
31 ### Seq 2
32 74	Label seq2 1
33 76	LoadRow	DmdStartRow NumRows InumC MemStartRow 173 # (1080*40ns)*(4tics/us)=172.8
3478ResetGlobal1003580Jump selectLoop 1
For this sequence file the following labels are stored in the label RAM => "selectLoop"=>54 # Store value 54 to address 0
"seq0" =>58 # Store value 58 to address 1
"seq1" =>66 # Store value 66 to address 2
"seq2" =>74 # Store value 74 to address 3

Now, by changing the value in address 0 ("selectloop"), each of the three sequences can be selected: If set to 58 then seq0 is executed,
If set to 66 then seq1 is executed, If set to 74 then seq2 is executed, cxxzz


Rec nametot_sizerec_idpayload
Reply2 bytes2 bytes2 bytes2 bytesSetSeqLabel8204addressdataReplyAckRequestSeqLabel6404addressReplySeqLabelReplySeqLabel8604addressdata-

6 in LB 4600 - Short User Guide
This section describes how to display images on the DMD on the Luxbeam 4600. There are two modes of displaying images, scrolling or non-scrolling images. It is assumed that the DMD-size is 1920x1080 in the following sections.


6.1 Non-scrolling Images
To display a single image of the size of the DMD the procedure described next can be followed.


6.1.1 Set Image Type (One-time Operation)
Set the image format to be sent using the record described in 5.2.2. This parameter is stored permanently in

Luxbeam 4600 and is normally set once only. Currently only must be set to 1 (binary).

are supported, so image type


Set image type to 1 (binary) and receive ok:

Send000600670001Receive000601F50000


6.1.2 Set Inum Size (One-time Operation)
Before loading an image into memory, the desired inum size must be set. This record is described in 5.2.1. The inum size is the number of lines that one complete image occupies in memory. This parameter is stored permanently in the Luxbeam 4600 and is normally set once only. So, for a 1920x1080 image the inum size should be set to 1080.

Set inum size to 1080 and receive ok:

Send000600660438Receive000601F50000


6.1.3 Load Image(s)
To load an image of 1920x1080 size into the start of the memory (Inum 0, offset 0) there is a sequence of records that must be sent.

Start by resetting the expected sequence number in the Luxbeam 4600, described in 5.2.11.

Reset sequence number counter to 1 and receive ok:

Send00040070Receive000601F50000

The sequencer inside the Luxbeam 4600 must be reset and disabled before loading an image to memory.

Disable the sequencer and receive ok:

Send0006006A0100Receive000601F50000

Set sequencer in reset-state and receive ok:

Send0006006A0201Receive000601F50000





Send 1st packet (sequence no. 1, inum 0, line offset 0):

Send05A E0068000100000000000000001440 bytes of data



Send 2nd packet (sequence no. 2, inum 0, line offset 6):

Send05A E0068000200000000000000061440 bytes of data

(Send 3rd - 179th packets in similar way...)


Send 180th packet (sequence no. 180, inum 0, line offset 1074):

Send05A E006800B400000000000004321440 bytes of data

There are no acknowledgements to the above image data packets. Hence, there must be a way to check if packets are not received correctly by the Luxbeam 4600 for some reason. To do this use the Sequence Number Error-record described in 5.2.10. This check can be done at any time, but in this example it is done after the complete 1920x1080 image has been transmitted.


Ask for sequence number error state and receive the answer:

Send00040137Receive000701FF010096

In this example there was an out-of-sequence error, meaning that sequence number 150 (0x96) was the last packet received ok. Hence, re-send the packets from 151 to 180 again.

Send 151st packet (sequence no. 151, inum 0, line offset 900):

Send05A E0068009700000000000003841440 bytes of data

(Send 152nd - 179th packets in similar way...)


Send 180th packet (sequence no. 180, inum 0, line offset 1074):



Send05A E006800B400000000000004321440 bytes of data

Do a new request for out-of-sequence packets:

Ask for sequence number error state and receive the answer:

Send00040137Receive000701FF000000
This time all packets were received ok by Luxbeam 4600 and the image is now stored in memory at inum 0.

If desired, different images can be loaded into other parts of the momory (inum 1, inum 2, etc) using the above command-sequence. In this way it is possible to have many images loaded in memory simultaneously and the selection of which image to be displayed is done in the sequence file that is currently running.
Loading of sequence file is described next.


6.1.4 Load Sequence File
A sequence file is a text file that must be transferred to Luxbeam 4600. The format of the file and the valid sequence-language commands are described in "6501560 - IS - Luxbeam 4600 Sequencer Language".

Below is a very simple sequence file, that will display the image that is loaded into inum 0.

#-------------------------------------------------------------------------------------
#CommandParametersWaitforComment#-------------------------------------------------------------------------------------
AssignVar	Inum 0	1	# Inum = 0LabelStartHere1# Start of loopLoadGlobalInum400# Load data from Inum (0) to DMDTrig1 40# Neg. edge internal triggerResetGlobal40# Display contents on DMDJumpStartHere1# Jump to start of loop
The above contents is loaded into Luxbeam 4600 using the record described in 5.3.1. The length of the data above is 517 bytes and will fit within one packet.

Send sequence file and receive ok:

Send020F0069000100010205517 bytes of data (23 2D 2D 2D 2D 2D...)


Receive000601F50000
Receiving "ok" back means that the syntax of the file sent was ok.



6.1.5 Start Sequencer
The final step to get the image displayed on the DMD is to take the sequencer out of reset and start it as described in 5.3.3.


Take sequencer out of reset-state and receive ok:

Send0006006A0200Receive000601F50000

Start the sequencer and receive ok:

Send0006006A0101Receive000601F50000
Now the image shold be displayed on the DMD.


6.2 Scrolling Images
It is the sequence files that controls if the image is to be scrolling or not. The image loading is done in the same way for both scrolling and non-scrolling images.


6.2.1 Set Image Type (One-time Operation)
See 6.1.1.



6.2.2 Set Inum Size (One-time Operation)
See 6.1.2.



6.2.3 Load image(s)
In this example an image of size 1920x3240 pixels will be scrolling up and down. This can be loaded as a single file of 1920x3240 at inum 0 or as three 1920x1080 images at inum 0, inum 1 and inum 2 respectively. In the following example the first option will be used.

Reset sequence number counter to 1 and receive ok:

Send00040070Receive000601F50000

The sequencer inside the Luxbeam 4600 must be reset and disabled before loading an image to memory.

Disable the sequencer and receive ok:

Send0006006A0100Receive000601F50000
Set sequencer in reset-state and receive ok:

Send0006006A0201Receive000601F50000

Then, the image data can be sent, as described in 5.2.3. The binary image data (which is a 1-bit .bmp file with the bitmap header (62 bytes) removed) must be split into packets of an integer number of lines. For a 1920x1080 DMD each packet can be from 1 to 36 lines, because 36 lines takes almost one full Jumbo frame packet (36*1920/8 bytes = 8640 bytes). As an example, we try to keep the packet size within standard 1500- bytes IP packet. Then the number of lines that can be sent in one packet is 6 (6 * 1920/8 bytes = 1440 bytes). The complete image will require 540 packets (540 * 6 lines = 3240 lines). Remember to send these packets to port 52986.

Send 1st packet (sequence no. 1, inum 0, line offset 0):





Send05A E0068000100000000000000001440 bytes of data

Send 2nd packet (sequence no. 2, inum 0, line offset 6):

Send05A E0068000200000000000000061440 bytes of data

(Send 3rd - 539th packets in similar way...)


Send 540th packet (sequence no. 540, inum 0, line offset 3234):

Send05A E0068021C0000000000000CA21440 bytes of data

Do a request for out-of-sequence packets:

Ask for sequence number error state and receive the answer:

Send00040137Receive000701FF000000

This time all packets were received ok by Luxbeam 4600 and the image is now stored in memory at inum 0 - 2.

7 RLE compression schemes

7.1 RLE compression Scheme for lb4k6
The run length encoding must terminate on each row, i.e. no run-length encoding can span from one row to the next.

Bit 15RLE1 =>RLE
0 =>RAWBit 14rle dataActual data for the full run lengthBit 13:11transitionTransition position in the byte that separate two run-lengthBit 10:0run lengthRun length in term of bytesBit 7:0raw dataData when raw mode is used
Example: 00|00|00|00|00|00|00|1F|FF|FF|FF|FF|FF|00|1f|FF|FF|FF
|	A	|	B	| C |D|
A: RLE=1, rle data=0, run-length=8, transition=3 B: RLE=1, rle data=1, run-lenght=5, transition=0 C: RLE=0, raw data = 00
D: RLE=0, raw data= 1F

7.2 RLE compression Scheme for lb4k7 - image type 2
RLE mode (bit15 = 0)

Bit 150RLE descriptorBit 14dataActual data for the full run lengthBit 13:0run lengthRun length in term of dwords(32 bits)
RAW - mode 0 (Bit15=1, Bit14=0)
Each descriptor define two dword. The coded dwords are selected from a lookup table where the address to this lookup table is the code found in the descriptors




Bit 151RAW descriptorBit 140RAW descriptor mode 0 ? two RAW dwords are decodedBit 13:7code for data1Lookup address for RAW dataBit 6:0code for data0Lookup address for RAW data
RAW decoding - mode 1 (Bit15=1, Bit14=1, Bit13=0)
Each descriptor define one dword. The coded dwords are selected from a lookup table where the address to this lookup table is the code found in the descriptors

Bit 151RAW descriptorBit 14:1310RAW descriptor mode 1 ? one RAW dword is decodedBit 10:0code for data1Lookup address for RAW data
RAW decoding - bytes (Bit15=1, Bit14=1, Bit13=1)
Each descriptor define one byte. This descriptor must be used in chunks for 4 descriptors (resulting in 4*8 bits) in order to stay aligned with the other descriptors that define dwords (32-bit)

Bit 151RAW descriptorBit 14:1311RAW byte descriptor ? one RAW byte is decodedBit 7:0dataOne byte of data

7.3 RLE compression Scheme for lb4k6 - image type 5

Bit 0data Adata ABit 10-1run length Arun length in terms of bits for data ABit 11data Bdata BBit 15-12run length Arun length in terms of bits for data A
Example
First RLE packet of one row contains the following data:
??? First symbol 0, Run length 2
??? Second symbol 1, Run length 3
??? Third symbol 0, Run length 1
??? Fourth symbol 1, Run length 5
This should be unpacked to the 11 bits "00111011111". If the next RLE packet arrives with the following data:



??? First symbol 0, Run length 1
??? Second symbol 1, Run length 1
??? Third symbol 0, Run length 1
??? Fourth symbol 1, Run length 1

...it should be decompressed directly behind the previous bits. The result would be the 15 bits "001110111110101". After several more RLE packets a complete row (1920 bits) will be filled. The last RLE packet will always end exactly at the end of the row and not continue to the next row.
